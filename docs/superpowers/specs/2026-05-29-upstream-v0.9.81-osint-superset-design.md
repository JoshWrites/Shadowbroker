## Goal

`origin/JoshWrites Shadowbroker` becomes a **functional superset of OSINT/dashboard capability**: every upstream advance in the OSINT/dashboard domain through v0.9.81, plus all of Josh's custom features and unioned datasets. Josh's remote receives the work; upstream is pull-only.

## Scope decision (explicit)

**IN scope** — pull from upstream v0.9.81:
- New OSINT data fetchers and their data sources
- New map layers, dashboard panels, popups, timeline UI
- Security hardening relevant to the web/backend dashboard
- Bug fixes, data-source attribution, fetcher enhancements
- Dataset growth (union, see below)

**OUT of scope** — deliberately NOT pulled (Josh runs via Docker/browser; these are unused subsystems and would add Rust toolchain + heavy build + crypto/governance surface):
- **Infonet** governance/proof-of-stake/crypto engine (~115 files)
- **Tauri desktop shell** (`src-tauri/`, ~59 files, needs Rust)
- **privacy-core** Rust→WASM library and its attestation/claims services
- Mesh privacy hardening tied to the above (DM private transport, wormhole root transparency, etc.) — except where a fetcher/dashboard feature needs it
- uv build-system migration (stay on existing pip/requirements flow unless a needed feature forces it)

Verified separable: all 10 new OSINT fetchers import **no** infonet/mesh/privacy/wormhole modules. Fetcher registration uses the same `services/fetchers/_store.py` pattern Josh already has. Upstream `main.py` is still a monolith (12k lines), not a hard router cutover — so OSINT pieces graft into the existing structure.

## Integration strategy

**Selective additive integration into Josh's branch** (NOT a fresh base off v0.9.81).

Rationale: a fresh v0.9.81 base would import all excluded subsystems by default, forcing risky removal against interdependencies. Merging selectively into Josh's branch keeps his architecture (demand-driven, all-layers-off, listener service, Pikud) as the foundation and adds exactly the OSINT surface wanted.

Mechanics: work on a new branch; bring in upstream OSINT files/changes by targeted checkout + adaptation rather than a blind `git merge upstream/main` (which would stage all 596 upstream-only files). Each logical group becomes its own commit producing a buildable state.

Verification rule: for any diverging dataset, after merge assert `merged_count >= max(yours, theirs)` and that no entry unique to either side was dropped.

## Risks & mitigations

- **Hidden coupling** of an in-scope OSINT feature to an excluded subsystem → detect at integration per group; if found, either stub the dependency or pull the minimal supporting module, documented.
- **Frontend build breakage** from partial component set → build after each frontend group; new components referencing Zustand store get adapted to Context or deferred if not OSINT-essential.
- **Backend import errors** from routers referencing excluded services → only register in-scope routers; leave excluded ones out of app wiring.
- **Dataset regression** → count-assert before/after.
